# Календарный HTTP API v1

Публичная документация: `/calendar-api`, кнопка «API календаря» на главной.
Установочный WordPress-плагин: `/downloads/orthocal-1.3.24.zip`.
Тарифы и выдача ключей: раздел «API календаря» в админке. На сайте отображаются
только включённые и опубликованные тарифы; цены не означают автоматической оплаты.

API использует тот же TypeScript-движок и XML, что редактор. JSON возвращается
без фильтров печатной сетки и без сокращения списка до помещающихся в ячейку
праздников. Правила движка (включая устранение дублей и выбор служб) сохраняются.
Это интерфейс к имеющимся данным, не новая аттестация их безошибочности.

## Адреса и параметры

После развёртывания `npm run build` базовый адрес:
`https://kalender.georg-kloster.ru/api/v1/calendar/`.
На немецком домене работают те же пути; язык задаётся параметром, не доменом.

| Запрос GET | Результат |
| --- | --- |
| `/api/v1/calendar/` | Версия данных, доступные языки, профили и пределы лет |
| `/api/v1/calendar/today` | `{metadata, day}` за сегодня без ключа |
| `/api/v1/calendar/day?date=2027-05-02` | `{metadata, day}` |
| `/api/v1/calendar/month?year=2027&month=5` | `{metadata, year, month, pascha, fastingPeriods, days}` |
| `/api/v1/calendar/year?year=2027` | `{metadata, year, pascha, fastingPeriods, days}` |
| `/api/v1/calendar/pascha?year=2027` | `{metadata, year, pascha}` |
| `/api/v1/calendar/upcoming?date=2027-12-30&limit=5&filter=main` | `{metadata, from, until, items: [{date, oldStyleDate, event}]}` |
| `/api/v1/calendar/service?date=2027-06-06&office=sixth-hour` | План службы по дате: круги, вставки и сокращения |

Месяц и год принимают `view=summary`: сохраняются даты, дни недели, стиль дня,
правило пищи, количество событий и краткие представления памятей без XML/raw,
чтений и коллекций изображений. Полный ответ остаётся значением по умолчанию.
Краткое представление не обрезает список памятей по вместимости ячейки.

`upcoming` требует ключа, включает начальную дату и ищет на 366 дней вперёд,
включая переход через Новый год, в пределах 1900–2200. `limit`: 1–10.
Фильтры: `main` (ранги 0–2 и 9), `twelve` (0–1), `great` (2),
`memorial` (9), `all` (0–9), только категория `commemoration`.
Количество относится к событиям, а не уникальным датам; при недостатке событий
ответ короче `limit`. Один запрос расходует одну единицу квоты.

Общие необязательные параметры:

- `lang=ru|cu|de|uk|pl`, по умолчанию `ru`. Это языки **календарных текстов**,
  не перечень языков интерфейса сайта. Английского календарного перевода сейчас нет.
- `profile=typikon-strict|parish`, по умолчанию `typikon-strict`.
  Профиль явно возвращается в JSON; это не личное предписание меры поста.

Диапазон API: **1900–2200**, границы включены. Входная дата — григорианская
гражданская дата `YYYY-MM-DD`, независимо от часового пояса компьютера.
Исторические годы используют текущую редакцию базы, а не реконструкцию
месяцеслова соответствующего исторического года.

## Что есть в ответе дня

- `date`, `oldStyleDate`, `weekday` (0 — воскресенье), `weekdayName`.
- `pascha`, `daysFromPascha` (отрицательное значение до Пасхи).
- `fasting`: профиль, период, правило пищи, поминовение, основание и источники.
- `foodLabel`, `fastingColor`, `foodMarkers`, `memorialMarkers`, `dayStyle`.
- `events` и `eventCount`: все события, оставленные календарным движком.
- `icons`: названия памятей икон, определяемые по русскому названию события.
  `imageUrl: null` означает, что привязанного изображения нет. Это не отдельный
  аттестованный каталог икон; полный исходный текст всегда остаётся в `events`.

Каждое событие содержит:

- полный `title`, исходный `sourceTitle`, исходные краткие варианты
  `shortTitle`/`veryShortTitle`, `typeCode`, `priority`, `description`;
- `category`: память, чтение, правило поста, сплошная седмица или правило венчания;
- `typikonMark`: наш идентификатор знака, русская подпись, SVG и печатный PNG,
  либо `null` — обычным памятям знак не добавляется;
- `sourceId`, `sourceIndex`, `source` с исходными полями XML, включая `raw`;
- дату, границы интервала, положение внутри интервала и `ruleKind`;
- `localization`: `source`, `exact`, `structured` или `source-fallback`.

`source: null` обозначает событие, созданное расчётом, а не самостоятельной
XML-записью. Библейские чтения представлены имеющимися ссылками и подписями;
полных библейских текстов в базе нет. Все остальные имеющиеся поля источника
доступны внутри `source`, а не теряются при сериализации.

## Богослужебный план службы

`GET /api/v1/calendar/service` — защищённый тем же API-ключом маршрут для
читателей Часослова, Telegram и других приложений. Он возвращает не библейский
текст, а всё, что определяется календарной датой: суточный круг, день седмицы,
подвижный период от Пасхи, глас, памяти дня, выбранные тропари/кондаки и
раскрытые общеупотребительные сокращения.

Пример:

```
/api/v1/calendar/service?date=2027-06-06&office=sixth-hour&lang=cu&expansion=full
```

Параметры:

- `date` — обязательная гражданская дата `YYYY-MM-DD`, 1900–2200;
- `office` — один из `midnight-office`, `matins`, `first-hour`, `third-hour`,
  `sixth-hour`, `ninth-hour`, `vespers`, `compline`, `typica`;
- `lang` и `profile` имеют тот же смысл, что у `/calendar/day`;
- `expansion=short|full` выбирает сокращённый или полный текст формул
  «Приидите, поклонимся», «Трисвятое», «Отче наш», «Слава, и ныне» и
  `Господи, помилуй` с указанным числом повторений.

Корень ответа содержит `date`, `office`, `cycles`, `assignments`, `expansions`
и `coverage`. `cycles.daily`, `cycles.weekly`, `cycles.movable` и
`cycles.annual` описывают соответственно суточный, седмичный, подвижный и
годовой круг. `assignments` содержит готовые тексты с устойчивым `textId`,
слотом (`troparion-of-day` либо `kontakion-of-day`) и источником. Редакционные
пометки и внутренний статус проверки в публичный ответ не входят. Полный Часослов и библейские места не дублируются:
клиент соединяет свой текст последования с этими календарными вставками.

На первом этапе автоматически выбраны воскресные гласы и тексты дней седмицы.
Все памяти и праздники дня уже возвращаются в `cycles.annual`; если для памяти
ещё не внесён проверенный собственный текст, ответ не подменяет его общим
тропарём. Такое ограничение видно в `coverage`, поэтому приложение не выдаёт
предположение за уставное назначение.

При `source-fallback` название остаётся русским. Описания, подписи знаков,
обоснования поста и исходные краткие названия также могут быть русскими:
параметр `lang` не обещает полный перевод всего JSON. Статус `exact` описывает
выбор словаря, а не независимую филологическую аттестацию строки.

Метаданные включают версию контракта, отпечаток данных `dataVersion`, статистику
XML, диагностические предупреждения, версию постных правил и границы полноты.
Изображения имеют пути от корня API-домена, например
`/assets/typikon/great.svg`; для другого сайта используйте `new URL(path, apiUrl)`.
Фотографии пользователей и их частные события не выдаются.

## Использование в JavaScript

```js
const base = 'https://kalender.georg-kloster.ru/api/v1/calendar/';
const url = new URL('day', base);
url.searchParams.set('date', '2027-05-02');
url.searchParams.set('lang', 'ru');
url.searchParams.set('profile', 'typikon-strict');
// Серверный код: API_KEY берётся из закрытой конфигурации, не из браузера.
const response = await fetch(url, { headers: { 'X-API-Key': process.env.CALENDAR_API_KEY } });
const data = await response.json();
if (!response.ok) throw new Error(data.message || data.error);
console.log(data.day.events);
```

## Ключи и публичный доступ

Без ключа доступны discovery `/api/v1/calendar/`, сегодняшний день `/today`
и опубликованные включённые тарифы `/api/v1/calendar-access/plans`.
Сегодня определяется на сервере в Europe/Berlin, григорианская дата.
У `/today` разрешены только `lang` и `profile`; дата, год, месяц и другие
параметры дают 400. Произвольный день, месяц, год и Пасха требуют ключа.

Передавайте ключ только в заголовке `X-API-Key: cal_…` (также поддерживается
`Authorization: Bearer cal_…`). Ключи в query не принимаются. IP-привязки нет.
Ключ BibleDesktop хранится в серверной конфигурации, а запрос выполняется
сервером BibleDesktop. Не включайте его в клиентский JavaScript и репозиторий.
Оба проекта могут находиться на одном сервере; HTTP-контракт остаётся тем же.

Владелец создаёт клиента в супер-админке `/admin/api`: имя, e-mail, тариф,
срок действия. Открытый ключ показывается только при создании/ротации;
в `CALENDAR_DATA_DIR/api-access.json` вне document root хранится SHA256.
Отключение клиента или тарифа прекращает доступ; дата окончания включительна
по UTC. Ротация немедленно отменяет старый ключ и сохраняет счётчики.
Стоимость тарифов информационная, расчёты и предоставление доступа ручные.

Лимиты минуты, дня и календарного месяца считаются по UTC, атомарно под lock.
Успешная авторизация валидного запроса расходует единицу, включая HEAD, 304
и последующую ошибку расчёта 503. Неверные параметры, неизвестные маршруты,
отсутствующие/неверные ключи не расходуют квоту. Discovery и today её не расходуют.
Остаток: `X-API-Month-Limit`, `X-API-Month-Remaining`. При 429 учитывайте
`Retry-After`. Глобальное ограничение публичного трафика — на nginx/CDN.

CORS `Access-Control-Allow-Origin: *` применяется только к календарным
маршрутам, credentials не разрешены. Админские маршруты требуют действующей
owner cookie; изменения дополнительно проверяют Origin.

Owner HTTP endpoints (серверные ответы всегда no-store):
- GET/PUT `/api/v1/admin/calendar-api`: обзор/тарифы и настройки, PUT требует revision.
- POST `/api/v1/admin/calendar-api/clients`: создать клиента, ответ {client,key}.
- PUT `/api/v1/admin/calendar-api/clients/{id}`: изменить клиента с revision.
- POST `/api/v1/admin/calendar-api/clients/{id}/rotate`: {revision}, ответ {client,key}.

## Тестовая страница

`public/calendar-api-test.html` — демостраница со встроенными JavaScript и CSS.
Откройте `/calendar-api-test.html` на сайте, выберите дату, язык и профиль.
API-ключ и регистрация не нужны; квот на число запусков нет. Локальная копия
или копия на другом сайте не получает демодоступ.

Страница использует отдельный `POST /api/v1/calendar-demo/day` с проверкой
Origin, Referer (путь тестовой страницы), Sec-Fetch-Site и X-Calendar-Demo.
CORS для демомаршрута отключён, доступны только публичные данные одного дня.
Это ограничение для браузеров, а не удостоверение подлинности клиента:
внешняя программа может имитировать заголовки. Скрытых API-ключей нет;
обычные API-маршруты по-прежнему требуют ключ. Серверный кэш и ограничения
ресурсов расчёта сохраняются.

Страница показывает все события, наши знаки Типикона, значок поста, исходные
поля и полный JSON; ответ можно скачать. После сборки та же страница доступна
по `/calendar-api-test.html`. Не вставляет полученные тексты через `innerHTML`.

## Развёртывание, нагрузка и ошибки

`npm run build` собирает также `dist/api/calendar-runtime.mjs` — самодостаточный
Node-модуль без Vue, браузера и зависимости от установленного `node_modules`.
Путь к текущему Node автоматически записывается при сборке на сервере.
PHP должен иметь разрешённый `proc_open` и доступ к этому исполняемому файлу.
При необходимости в `.env` задаётся `CALENDAR_NODE_BINARY=/absolute/path/to/node`.
Сборку следует выполнять на сервере, а не переносить Windows-путь к Node в Linux.

Постоянный Node-сервис и дополнительный порт не требуются: PHP запускает Node
при отсутствии рассчитанного года в кэше, затем процесс завершается.
Кэш находится в `CALENDAR_DATA_DIR/public-calendar-cache`, по умолчанию
`storage/public-calendar-cache`, вне document root. Сохраняется не более 32
годовых ответов (обычно порядка 200–300 МБ суммарно), старые вычисляемые файлы
удаляются автоматически. Пользовательские данные не затрагиваются.
Годовой ответ содержит несколько мегабайт: для виджета дня запрашивайте `/day`.

Ключ кэша включает год, язык, профиль и хеш движка/XML/церковнославянского
словаря. На промахе кэша подпись файлов проверяется до и после вычисления,
чтобы не сохранить смешанную версию во время публикации. Доступен один
одновременный расчёт; другие запросы на ещё не рассчитанные годы получают
`503 calendar_busy` с `Retry-After: 2`. Кэшированные запросы обслуживаются отдельно.
Предел процесса — 20 секунд и 256 МБ JS heap; размер вывода ограничен.

Ответы GET/HEAD содержат `ETag`, поддерживают `If-None-Match` и 304, публичный
HTTP-кэш отключён: `Cache-Control: private, no-store` (включая ошибки). Каждый
защищённый запрос проходит авторизацию и квоту даже с ETag; для большого публичного
трафика настройте дополнительное ограничение частоты на nginx/CDN.

Успешные ответы дополнительно дают `X-Calendar-Application-Cache-TTL: 300`.
Это явное разрешение серверным интеграциям хранить разобранные календарные данные
до пяти минут, не разрешение HTTP/CDN-кэширования. Ключ прикладного кэша должен
включать учётные данные и все параметры запроса. После истечения TTL нужно снова
обратиться к API; просроченные ответы при ошибках не выдаются. Исправления базы,
отзыв и окончание доступа проявляются в интеграциях в пределах этих пяти минут.
Авторизация и квоты по-прежнему проверяются при каждом фактическом запросе API.
Старые серверы без этого заголовка не разрешают плагину постоянное кэширование.

Ошибки возвращаются JSON: `{error, message}`. Основные статусы:

- 400: неверная дата, год, месяц, язык, профиль или массив вместо параметра;
- 401: отсутствующий или недействительный API-ключ;
- 403: отключённый клиент/тариф или истёкший ключ;
- 429: исчерпана квота минуты, дня или месяца;
- 404: неизвестный маршрут;
- 405: запись запрещена, разрешены только GET/HEAD/OPTIONS;
- 503: API не собран, недоступен Node, идёт обновление, расчёт занят или не удался.

Техническая ошибка Node пишется в PHP error log (журналы домена в Plesk),
без выдачи внутренних путей и стека клиенту. После изменения XML/движка
обязательно повторяйте `npm run build`.

Проверка локально:

```bash
npm run build
npm test
npm run test:calendar-api
```

Последняя команда поднимает изолированный PHP-сервер, проверяет HTTP и открывает
опубликованную демостраницу без ключа в браузере. На Windows используется установленный Edge;
на других системах нужен Chromium для Playwright. Производственный сайт тест не меняет.

## Системные интеграции

Владелец может выбрать тип клиента `system` в `/admin/api` для BibleDesktop
и других собственных серверных интеграций. Это отдельный тип доступа, не тариф.
В owner POST/PUT клиента передайте `kind: "system"`, `planId: null`.
Для обычного доступа используется `kind: "standard"`; существующие клиенты
без поля kind остаются обычными. Переключение типа доступно только владельцу.

Системному ключу не назначаются квоты минуты, дня и месяца; отключённые тарифы
его не блокируют. Отключение самого клиента, срок действия и ротация действуют
как обычно. Счётчики запросов продолжают обновляться. Смена типа и ротация
не сбрасывают использование. Для системного ключа заголовки
`X-API-Month-Limit` и `X-API-Month-Remaining` отсутствуют, а внутренний результат
авторизации содержит null вместо числового лимита. Обычные клиенты продолжают
подчиняться тарифам. Ключи обоих типов дают только чтение календарных данных:
управление админкой по API-ключу невозможно. Системный тип не публикуется
в перечне тарифов, публичного безлимитного тарифа нет.

## Тексты чтений на тестовой странице

`calendar-api-test.html` сначала получает каталог `https://bible-desktop.com/api/translations`,
проверяет `language.code` и предлагает отдельные язык Библии и перевод.
При первом запросе язык Библии совпадает с языком календаря; после явного выбора
сохраняется выбор пользователя в памяти страницы. Если перевода выбранного языка
нет, показывается ошибка без автоматической подмены русским.

Для каждого структурированного `event.reading` с `parseStatus=parsed` страница
сопоставляет OSIS с `canonical_book.osis_code` каталога книг выбранного перевода,
затем получает главы и выводит `verses[].plain_text`. Порядок отрывков, переходы
глав, пропуски между отрывками и повторения сохраняются. Одновременно выполняются
не более трёх запросов BibleDesktop; главы кешируются в памяти по переводу, slug
и номеру главы. Смена перевода защищена от запоздалых ответов прошлого запроса.

Неполный разбор, отсутствующая книга/глава/стих, разрыв номеров и несовпадение
языка показываются ошибкой; частичный текст не выдаётся как полное чтение.
Предупреждение о неподтверждённом соответствии нумерации сохраняется всегда.
Календарный ключ отправляется только календарному API, не BibleDesktop;
тексты вставляются как textContent. Каталог можно обновить отдельной кнопкой.

Оба сервера требуют обновления: календарь должен выдавать `event.reading`,
BibleDesktop — `translation.language` в книгах/главах и `verses[].plain_text`.
При старой схеме страница явно сообщает, какой API требуется обновить.
Проверка браузерной интеграции без обращений к production:
`node scripts/test-calendar-bible-texts.mjs`.

## Богослужебный справочник

`GET /api/v1/calendar-texts/` использует тот же API-ключ и квоты календаря.
Начальная библиотека содержит 98 церковнославянских текстов: тропари, кондаки,
молитвы и величания. Фильтры: `id`, `type`, `scope`, `tone`, `weekday`, `language`.
Например: `/api/v1/calendar-texts/?type=troparion&scope=resurrection&tone=1`.
Ответ включает `version`, `contentHash`, `count`, `texts` и
`assignment: reference-only`. Внутренние поля `review`, `note`, `completeness` и
`availability` удаляются на границе публичного API. GET/HEAD/OPTIONS, ETag/304, прикладной кэш 300 секунд.
Неизвестный ID даёт 404, неверные параметры — 400, неизвестный язык — пустой список.
Тексты не назначаются дню автоматически.
Источники и ограничения: `docs/LITURGICAL-TEXTS.md`.
