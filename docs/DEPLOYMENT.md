# Развёртывание `kalender.georg-kloster.ru` в Plesk

Производственная версия состоит из статического интерфейса в `dist` и небольшого
PHP-обработчика в `dist/api`. PHP обслуживает подтверждение e-mail, общие ссылки,
блокировку редактирования, настройки, общие макеты, загрузку PDF и публичный
календарный API. Постоянная Node.js-служба и дополнительный порт не нужны.

Рабочий каталог:

```text
/var/www/vhosts/georg-kloster.ru/kalender.georg-kloster.ru
```

## Первая сборка и обновления

Команды выполняются системным пользователем сайта, не `root`:

```bash
cd /var/www/vhosts/georg-kloster.ru/kalender.georg-kloster.ru
git pull --ff-only origin main
nodenv local 22
npm ci --include=dev
npm run build
mkdir -p storage
chmod 700 storage
```

Node.js используется для сборки и для расчёта публичного календарного API при
промахе серверного кэша. PHP кратковременно запускает собранный модуль через
`proc_open`; постоянный процесс не работает. Путь к Node записывается автоматически
при серверной сборке; при необходимости задайте `CALENDAR_NODE_BINARY` в `.env`.
PHP должен иметь право запуска Node и записи в `storage/public-calendar-cache`.
`npm prune --omit=dev` допустим: собранный календарный модуль самодостаточен.
Проверка после обновления: `/api/v1/calendar/day?date=2027-05-02`.
Подробности и тестовая HTML-страница: [Календарный HTTP API](CALENDAR-HTTP-API.md).

### Обновление без поломки открытых вкладок

Используйте именно `npm run build`, не `npx vite build` и не удаление `dist`.
Команда сначала проверяет TypeScript, затем собирает сайт во временной папке
`tmp/site-build-*` вне document root. Только успешная сборка публикуется в `dist`:
сначала файлы, последним — `index.html`. Каждый файл заменяется через переименование
готового файла из закрытой временной папки, поэтому посетителям не выдаётся
недописанный JavaScript/HTML или временная копия PHP-кода. `tmp` и `dist` должны
находиться на одной файловой системе; междисковая публикация отклоняется.
Ошибка компиляции не затрагивает работающую версию. Одновременные сборки запрещены
блокировкой `tmp/production-build.lock`. После аварийного завершения процесса
удаляйте только эту пустую папку блокировки, предварительно убедившись, что сборка
уже не работает.

Старые файлы с хешем в имени из `dist/assets` сохраняются целиком: экспортер,
общие зависимости, стили и другие ресурсы. Автоматического срока удаления нет:
нельзя определить, как долго посетитель держит редактор открытым. Не очищайте
эти файлы при обновлении и не используйте синхронизацию с удалением старых assets.
Каталог будет постепенно расти; очистка — отдельное обслуживающее действие с
согласованным сроком поддержки старых вкладок. Удалённые из исходников PHP-файлы
и остальные устаревшие неверсионированные файлы не сохраняются. Пользовательские
данные должны, как и прежде, оставаться в `storage` вне `dist`.

Это не атомарное переключение всего PHP-приложения: обновления API по-прежнему
должны оставаться совместимыми с открытыми клиентами. Здесь гарантируется порядок
публикации фронтенда, а не автоматическая совместимость разных версий API.

`public/.htaccess` включает перепроверку HTML (`Cache-Control: no-cache`) и
возвращает настоящий 404 для отсутствующих `assets`, `fonts`, `brand`, `data`,
не подменяя их главной страницей. Это соответствует описанию проблемы старых
динамических импортов в [документации Vite](https://vite.dev/guide/build.html#load-error-handling).
Если nginx/CDN обслуживает HTML напрямую, задайте там такую же политику кеша;
директивы Apache не действуют на ответы, которые не проходят через Apache.

После публикации проверьте на **обоих** доменах:

```bash
curl -I https://kalender.georg-kloster.ru/
curl -I https://kalender.georg-kloster.ru/account
curl -I https://kalender.georg-kloster.ru/assets/missing-deployment-check.js
```

Для первых двух ответов ожидается `Cache-Control: no-cache, max-age=0, must-revalidate`,
для третьего — HTTP 404. Запрос существующего `pdf-exporter-*.js` должен отдавать
JavaScript, не HTML. Старые файлы, уже удалённые предыдущими сборками, это обновление
не восстанавливает: такие вкладки нужно один раз обновить после сохранения работы.

Ошибки экспорта теперь также записываются в **F12 → Console** с префиксом
`[Calendar PDF: ...]` и этапом: `load-module`, `load-fonts`, `render-pdf`, `upload-pdf`.
При ошибке загрузки модуля показывается инструкция без автоматической перезагрузки
редактора; исходная ошибка сохранена в `cause`. Серверного журнала клиентских ошибок
или передачи содержимого календарей во внешнюю систему логирования это не добавляет.

Регрессии: `npx vitest run tests/build-publication.spec.ts tests/pdf-export-loader.spec.ts`
и `npm run test:build-update`. Последняя команда открывает реальный браузер с тестовой
сборкой, дважды обновляет её и только затем загружает старый PDF-модуль, его зависимость
и CSS из старой вкладки. Проверяет также новую вкладку и сохранность несохранённого
текста. Apache и production-аккаунты этот локальный тест не использует.

При первой установке создайте конфигурацию:

```bash
cp -n deploy/kalender.env.example .env
chmod 600 .env
nano .env
```

В `.env` заменяется `SMTP_PASSWORD`; параметры SMTP
должны соответствовать созданному в Plesk ящику. При обновлении не заменяйте
рабочий `.env` примером. Существующий `MAIL_FROM` поддерживается, новые
`MAIL_FROM_ADDRESS` и `MAIL_FROM_NAME` имеют приоритет. Файл находится выше
`dist` и не выдаётся посетителям сайта. Для локальной отправки через PHP/Plesk
доступен `MAIL_TRANSPORT=sendmail` без SMTP-пароля.

Для доставляемости писем включите в Plesk DKIM-подпись исходящей почты, а у
авторитетного DNS-провайдера домена опубликуйте показанную Plesk запись DKIM,
SPF для отправляющего сервера, а также DMARC. Пока DNS внешний, одной
галочки DKIM в Plesk недостаточно.

## Настройки Plesk

### Администратор, подписки и доступ браузера

Вход администратора отдельный, по логину и паролю, без e-mail. После обновления
под пользователем сайта выполните `php scripts/setup-admin.php`: скрипт
запросит логин и пароль (ввод пароля скрыт), сохранит `ADMIN_LOGIN` и
`ADMIN_PASSWORD_HASH` в `.env`, оставив настройки SMTP без изменений. Создаётся
резервная копия `.env.admin-backup-*` с правами 600 выше публичной директории.
Повторный запуск меняет пароль и отзывает ранее выданные административные сессии.
`CALENDAR_OWNER_EMAIL` больше не предоставляет административных прав.

Войти можно с главной страницы кнопкой «Администратор» или через меню
«Файл → Администратор». Этот же вход разрешает управление общими макетами.
Сессия действует 12 часов, хранится в HttpOnly / SameSite=Strict cookie
(Secure в HTTPS); на сервере хранится только хеш токена. Выход отзывает сессию.
Изменяющие запросы проверяют Origin; `APP_PUBLIC_URL` должен соответствовать
адресу приложения в браузере. После нескольких неверных паролей действует
короткая задержка до 60 секунд, а не блокировка по числу писем.
Права проверяются сервером на каждом административном
запросе. Раздел показывает серверные общие календари (с просмотром без захвата
блокировки), пользователей/подписки и последние 2000 событий отправки.
Локальные файлы и IndexedDB других браузеров не передаются в админку.

Подписка добровольная, галочка изначально снята. Одна ссылка подтверждает
адрес и подписку, только если согласие было отмечено при запросе письма.
Хранятся версия/текст согласия, даты запроса и подтверждения, история отписки.
Подтверждённые ранее адреса автоматически не подписываются. Отписка по ссылке
не требует входа и не отзывает доступ к календарям. GET показывает форму,
POST отписывает; просмотр ссылки почтовым сканером не отписывает пользователя.

Рассылка запускается владельцем вручную после проверки текста. Во время
отправки окно должно оставаться открытым; обрабатывается по одному получателю
на запрос. Подписка проверяется перед каждой отправкой. Ошибки и неопределённый
результат не повторяются автоматически во избежание дубликатов. «Принято
почтовым сервером» не означает доставку в ящик. Планировщика и автоматических
напоминаний пока нет. Включение DKIM/SPF/DMARC и политики обработки данных
остаётся обязанностью владельца сервера.

Подтверждённый браузер хранит токен в localStorage без календарного срока
истечения; новые подтверждения больше не вытесняют прежние браузеры. Очистка
данных сайта, другой браузер или отзыв токена требуют нового подтверждения.
При обновлении уже удалённые старой версией токены не восстанавливаются.

Письмо можно подтвердить на другом устройстве. При запросе новый клиент
получает отдельный случайный секрет браузера, который не входит в письмо.
До подтверждения он не даёт доступа. Переход по письму активирует только
исходный браузер; телефон показывает сообщение «Вернитесь к компьютеру».
Компьютер проверяет статус раз в 3 секунды (при ошибке сети — раз в 10 секунд)
и сохраняет вход. Запрос хранится в localStorage и восстанавливается после
закрытия вкладки. Старые письма и старые клиенты сохраняют прежнюю совместимость.

Антиспам использует `email-rate-limits-v2.json`: пауза 60 секунд после успешной
отправки на адрес, не более 100 успешных отправок с IP в час, одна одновременная
отправка на адрес/IP. Ошибки не расходуют квоту. Резерв при аварийном завершении
PHP истекает через 180 секунд. Старый файл счётчиков больше не используется.

Проверки без реальных писем: `php scripts/test-admin.php` и
`node scripts/test-admin-http.mjs`. Тестовые данные создаются только в `tmp/`.

Для субдомена включите обычный режим сайта с PHP 8.1 или новее и стандартный
режим проксирования nginx через Apache. В поле **Document root** укажите:

```text
/var/www/vhosts/georg-kloster.ru/kalender.georg-kloster.ru/dist
```

Если поле принимает путь относительно каталога подписки:

```text
kalender.georg-kloster.ru/dist
```

Поле **Дополнительные директивы nginx** должно быть пустым. Маршрутизация
`/api/...` уже находится в `dist/.htaccess`; Plesk передаёт эти запросы обычному
PHP-обработчику. Файл `dist/.user.ini` устанавливает лимиты для больших общих
проектов и длительных операций.

Максимально допустимый размер HTTP-запроса в Plesk можно оставить 128 МБ. PDF
передаётся частями по 4 МБ, а общий проект ограничен 100 МБ.

```bash
curl -fsS https://kalender.georg-kloster.ru/api/health
```

Ожидаемый ответ:

```json
{"ok":true,"collaboration":true,"runtime":"php"}
```

## Хранение данных

- До команды «Поделиться для совместной работы…» проект остаётся в браузере и
  локальном файле `.kalendar`.
- Общие проекты находятся в `storage/shared-projects`.
- Аренда редактирования хранится в `storage/leases`, действует 45 секунд и
  продлевается открытым редактором каждые 15 секунд.
- Подтверждённые адреса и настройки находятся в
  `storage/email-identities.json`.
- Общие макеты находятся в `storage/calendar-grid-templates.json`.
- PDF собираются потоково в `storage/pdf-exports` и скачиваются с поддержкой
  продолжения прерванной загрузки.

Каталог `storage` находится вне `dist`, поэтому nginx и Apache не могут отдать
его содержимое напрямую.
