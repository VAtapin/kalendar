# Аудит перед переходом редактора на API Bible Desktop: 08.10.2026

Этот отчёт фиксирует исходный аудит до миграции. После него реализован
переход на `/api/v1/calendar/editor-year`: BibleDesktop `c91448b4` исправляет
29 февраля и предоставляет версионированный снимок с обоими профилями.
Kalendar сохраняет снимок в документе и использует его в редакторе и PDF.
Текущее устройство и проверки: [снимки редактора](EDITOR-BIBLE-SNAPSHOTS.md).

Ниже описано состояние **до перехода**, размеры прежнего `/year?view=full`
и причины выбора нового контракта. Это не описание текущего редактора.

## Что проверено

Редактор загружает MemoryDays.xml и строит год в App.vue, AdminDialog.vue
и VisualGridEditor.vue. PageScene и PDF-exporter используют рассчитанные дни,
локальные правила поста, перевод/варианты заголовков и печатную геометрию.
Частные monasteryEvents добавляются отдельно. Общие HTTP-функции входа,
сохранения, заказов и печати не относятся к календарному поставщику.

Воспроизводимая проверка:

```bash
npx tsx scripts/audit-editor-bible-api.ts --live
```

Нужен соседний checkout BibleDesktop; другой путь задаётся BIBLE_DESKTOP_ROOT.
Без --live проверяется его локальный runtime. --live делает десять GET-запросов
годов 2027 с паузами 2.2 с; БД и production не изменяет. JSON-отчёт сохраняется
в tmp/editor-bible-api-audit.json. Код выхода 1 означает найденное различие,
а не успешную идентичность. Полный ответ/отчёт в Git не добавляется.

- XML двух проектов идентичен по SHA-256:
  8c1bef82656a0b39cd3d4ac8ffc33fc35f1ef123a728df93344931e914cf8ff4.
- 32 сопоставления с локальным runtime BibleDesktop: 11 686 дневных записей,
  138 508 событий (повторные варианты профиля/языка считаются отдельно).
- Годы: 1900, 1901, 2000, 2024, 2025, 2026, 2027, 2028, 2030, 2100, 2199,
  2200; в каждом оба профиля. Для 2027 дополнительно все пять языков.
- Десять настоящих ответов production API: весь 2027, пять языков × два
  профиля, ещё 3650 дневных записей. Проверены даты/старый стиль/Пасха,
  полный упорядоченный список событий, ID/исходное название/перевод/
  короткие названия/описание/приоритет/правило/интервал/styleToken,
  правила и периоды поста, стиль номера дня.
- Это выборка пограничных и рабочих лет, не исчерпывающая проверка всех
  301 лет или точного визуального/PDF-сравнения после будущей миграции.

## Обнаруженное несовпадение

У всех проверенных невисокосных юлианских годов различается один день:
редактор преобразует несуществующее 29 февраля в 1 марта старого стиля,
BibleDesktop проверяет валидность и пропускает запись. Для 2027 это 14 марта,
для 2199 — 15 марта из-за разницы календарей. Остальные проверенные поля
совпали; високосные юлианские годы из выборки совпали полностью.

Затронуты четыре записи:

| ID | Память |
| --- | --- |
| memory-day-0377 | Иоанн Кассиан Римлянин |
| memory-day-0887 | Девпетерувская икона Божией Матери |
| memory-day-1202 | Иоанн, нареченный Варсонофием, епископ Дамасский |
| memory-day-1203 | Феоктирист, игумен Пеликитский |

Не следует механически копировать ошибочное преобразование редактора в API.
Практика переноса на 28 февраля старого стиля подтверждена ответом священника
Афанасия Гумерова для всех четырёх памятей:
[Православие.Ru](https://www.pravoslavie.ru/6257.html).
Для XXI века в невисокосном году это 13 марта нового стиля. Исправление должно
быть явным правилом центрального ядра с тестами для високосных и невисокосных
юлианских лет, включая 1900/2100; в этой проверке оно не реализовано.

## Достаточность существующего контракта

| Потребность редактора | Состояние API |
| --- | --- |
| Полный год, Пасха, старый стиль, события и чтения | Есть /api/v1/calendar/year?view=full |
| Два профиля поста, пять языков, короткие названия | Есть, проверено сравнение |
| Типикон, приоритеты, описание, интервалы, исходные ID | Есть в полном ответе |
| Краткий month/year или /api/calendar/month | Недостаточен: отсекает чтения/пост/служебные поля |
| Дни с проверенными иконами | Только day добавляет галереи из БД; год не даёт полный каталог изображений |
| События монастыря, редакторские пометки, дизайн | Частные данные проекта; остаются в редакторе |
| Миллиметры, размещение, обрезка, шрифты, PDF/X | Функции редактора; не требуется перенос на календарный API |
| Неизменяемая версия данных/ETag/content hash | Сейчас отсутствует в публичном ответе |
| Готовый компактный печатный snapshot | Сейчас отдельного контракта нет |

Полный год измерен как 8 256 725–10 950 870 байт JSON до транспортного сжатия
(профиль/язык влияют на размер); первый проход занимал около 1.7–2.7 с,
повторный около 0.6–1.4 с. Источники событий и декоративные списки повторяются.
При смене языка/профиля нужен другой ответ. Десять запросов на весь набор не
обязательны для одного документа, но их нельзя выполнять на каждую перерисовку.

Публичный API ограничен 30 запросами/минуту на IP. Серверный cache и рекомендуемый
application TTL — 300 с; Cache-Control: no-store, private, ETag отсутствует,
CORS допускает прямой браузерный запрос. Эти ограничения подтверждены кодом,
реальными заголовками и чатом BibleDesktop. TTL не означает неизменяемость
данных и не разрешает молча заменять содержимое сохранённого печатного макета.

## Требования, реализованные после аудита

1. Исправить перенос 29 февраля в центральном BibleDesktop и проверить обе
   ветви календаря. Целевой результат должен быть корректным, а не повторять
   случайное переполнение даты старого редактора.
2. Добавить компактный versioned snapshot года для редактора: полный набор
   событий/чтений и правил поста, исходные названия, переводы/варианты,
   версия схемы/ядра/корпуса, content hash и tuple year/profile/language.
   Декоративные ресурсы/полные source-записи не повторять в каждом событии.
3. Загружать год один раз, проверять схему/диапазон/полноту, сохранять снимок
   рядом с документом и в локальном кеше. Открытие/печать прежнего проекта
   используют его снимок; обновление календарных данных — отдельное явное
   действие, не побочный результат фонового запроса.
4. Сейчас calendarData принудительно обнуляется в App.vue, project-storage,
   project-history и project-templates. Для снимка нужно совместимое изменение
   сохранения/открытия/миграции старых файлов; простая замена fetch недостаточна.
5. Одним адаптером переключить главный редактор, предпросмотр администратора,
   VisualGridEditor, экранный рендер и оба пути PDF. Сохранить локальные частные
   события, наборы декора, геометрию и печатную политику «поминовение вместо
   картинки поста». Извлекать готовые правила API без второго расчётного ядра.
6. Предусмотреть 429/Retry-After, тайм-аут, отсутствие сети и сохранённый снимок.
   Создание нового года без сети и без кеша честно недоступно; прежние проекты
   должны открываться/печататься. Проверить документы до и после миграции,
   смену года/языка/профиля, частные события, краткие названия и PDF.
7. Удалить дублирующие календарные расчёты из production-клиента только после
   этих проверок; отображение и печатные компоненты оставить локальными.

Вывод: рекомендуем единый BibleDesktop для всех публичных календарных
расчётов, с локально сохранённым снимком и частными данными проекта.
Эти требования выполнены новым контрактом и сохранением снимка в проекте;
production должен обновляться в порядке BibleDesktop → Kalendar.
