# План разработки

План построен так, чтобы сначала доказать точность печатной геометрии и
календарных расчётов, затем создать одну полноценную месячную страницу и только
после этого расширять визуальный редактор.

## Общие правила выполнения

- Каждый этап заканчивается работающим и проверяемым результатом.
- Следующий слой не рассчитывает данные предыдущего слоя повторно.
- Вся печатная геометрия хранится в миллиметрах.
- Vue-компоненты не являются моделью документа.
- Календарный движок не знает о шаблонах, SVG или PDF.
- PDF-движок не знает правил православного календаря.
- Исходный код WordPress-плагина не используется и не переносится.
- `MemoryDays.xml` является источником записей, но не исполняемого кода.
- Ошибки переполнения и предпечатной подготовки всегда видимы пользователю.

## Этап 0. Фундамент печатной сцены

Цель: получить независимую модель документа и пустой физически точный лист A3.

Работы:

1. Создать Vue 3 + TypeScript + Vite проект.
2. Ввести `CalendarProject`, `DocumentModel`, `PageModel` и `LayoutElement`.
3. Зафиксировать единицу документа `mm`.
4. Создать пустую страницу A3 Portrait 297 x 420 мм.
5. Заложить форматы A3, A4, A5 и A6 с обеими ориентациями.
6. Добавить постраничное дерево слоёв: один объект на лист дерева, пустые слои,
   вложенные папки, порядок, переименование, видимость и блокировку.
7. Добавить bleed 3 мм и safe area.
8. Реализовать чистое построение `PageScene` без Vue и DOM.
9. Создать экранный SVG-preview.
10. Добавить миллиметровые линейки и изменение масштаба.
11. Перестроить свойства в компактные раскрывающиеся панели.
12. Проверить геометрию автоматическими тестами.

Критерий готовности:

- изменение zoom не изменяет координаты документа;
- media box равен 303 x 426 мм;
- trim box равен 297 x 420 мм;
- страница отображается с линейками и служебными зонами;
- typecheck, тесты и production build проходят.

## Этап 1. Анализ и импорт `MemoryDays.xml`

Цель: превратить XML в строго типизированные исходные записи без потери данных.

Работы:

1. Добавить XML в отдельный каталог исходных данных.
2. Описать фактическую схему полей и допустимые значения.
3. Создать собственный безопасный XML-парсер.
4. Сохранить оригинальные числовые коды событий.
5. Разделить нормализованные поля и исходную запись.
6. Создать отчёт по количеству записей, типам и необычным значениям.
7. Добавить тестовые XML-fixtures для каждого обнаруженного варианта записи.

Критерий готовности:

- все записи XML читаются без исключений;
- ни одно исходное поле не теряется;
- неизвестный тип не приводит к падению и отмечается диагностикой;
- результаты импорта воспроизводимы и покрыты тестами.

## Этап 2. Собственный календарный движок

Цель: рассчитать календарные события выбранного года независимо от интерфейса.

Работы:

1. Создать date-only модель без зависимости от локального времени и DST.
2. Самостоятельно реализовать расчёт православной Пасхи.
3. Реализовать фиксированные даты из XML.
4. Реализовать переходящие даты как смещения относительно Пасхи.
5. Реализовать интервалы событий и специальные правила структуры XML.
6. Рассчитать интервалы постов из пасхального цикла и старостильных дат, а
   категории пищи — отдельным именованным профилем правил, не полагаясь на
   бинарный `type=10` из XML.
7. Формировать `OrthodoxCalendarDay` для каждого гражданского дня года.
8. Хранить полное, краткое и максимально краткое название события.
9. Добавить диагностику конфликтов и непонятных записей.

Критерий готовности:

- движок возвращает полный год без обращения к UI;
- фиксированные и переходящие события проходят контрольные тесты;
- расчёты одинаковы в любой системной временной зоне;
- каждое вычисленное событие связано с исходной XML-записью.

## Этап 3. Контроль правильности календаря

Цель: сделать расчёты проверяемыми до начала вёрстки.

Работы:

1. Добавить debug-выгрузку календарного года.
2. Создать контрольные наборы для обычных и високосных лет.
3. Проверить годы с ранней и поздней Пасхой.
4. Добавить выборочные ручные контрольные даты.
5. Проверять отсутствие дубликатов, потерянных событий и неверных интервалов.

Критерий готовности:

- проверяющий может увидеть происхождение и способ расчёта каждой даты;
- набор regression-тестов фиксирует согласованный результат календаря.

## Этап 4. Семантические стили и события монастыря

Цель: отделить смысл события от его визуального оформления.

Работы:

1. Ввести style tokens: `great-feast`, `sunday`, `fast`,
   `monastery-feast`, `ordinary-day` и другие фактические категории.
2. Создать настраиваемые приоритеты визуальных правил.
3. Добавить ежегодные и разовые `MonasteryEvent`.
4. Разрешить каждому локальному событию выбирать style token и значок.
5. Реализовать ручное переопределение отдельного дня.
6. Добавить встроенное сопоставление категорий поста с графическими знаками.

Критерий готовности:

- смена темы меняет оформление без изменения календарных данных;
- конфликты нескольких правил решаются предсказуемым приоритетом;
- количество событий монастыря не ограничено.

## Этап 5. Базовые layout-элементы

Цель: научить независимый рендерер строить содержимое страницы.

Работы:

1. Реализовать `TextElement`.
2. Реализовать `ImageElement` с fit, fill и crop.
3. Реализовать `ShapeElement` и `SvgElement`.
4. Добавить сортировку по `zIndex`, visibility и locking.
5. Реализовать реальные измерения текста выбранным шрифтом.
6. Добавить состояния overflow: `none`, `warning`, `error`.
7. Создать SVG-адаптер сцены, независимый от Vue.

Критерий готовности:

- одна модель страницы детерминированно рендерится в SVG;
- текст и графика располагаются по миллиметровым координатам;
- переполнение обнаруживается, а не обрезается молча.

## Этап 6. Интеллектуальная календарная сетка

Цель: собрать одну полноценную страницу месяца.

Работы:

1. Создать `CalendarGridElement` как специализированный layout-объект.
2. Реализовать составную ячейку дня: число, события, пост, значок и фон.
3. Добавить параметры шрифта, размера, межстрочного интервала и отступов.
4. Реализовать полное, краткое и очень краткое представление события.
5. Добавить последовательную стратегию размещения текста.
6. Поддержать 5 и 6 недель.
7. Поддержать объединяемые и свободные области сетки.
8. Добавить `MonthTextElement`, заполняющий только достаточно крупные свободные
   начальные или конечные ячейки и исчезающий при отсутствии места.
9. Добавить автоматически генерируемый `LegendElement`.

Стратегия переполнения:

1. полное название;
2. краткое название;
3. очень краткое название;
4. допустимое уменьшение шрифта;
5. скрытие событий низкого приоритета с предупреждением предпечатной проверки,
   но без надписи «ещё» на печатной странице;
6. ручное исправление пользователем.

Критерий готовности:

- выбранный месяц полностью отображается на одной A3-странице;
- ни одно переполнение не остаётся незамеченным;
- легенда содержит только реально используемые обозначения.

## Этап 7. Шаблон страницы месяца

Цель: получить вертикальный рабочий прототип календаря.

Работы:

1. Создать первый шаблон A3 Portrait.
2. Добавить область фотографии.
3. Добавить название месяца.
4. Разместить календарную сетку, текст месяца и легенду.
5. Добавить настройки темы и размеров областей.
6. Сформировать все 12 месяцев из одного шаблона.

Критерий готовности:

- проект на выбранный год содержит 12 корректных месячных страниц;
- изменение шаблона предсказуемо применяется ко всем месяцам;
- отдельная страница допускает локальное переопределение.

## Этап 8. Отдельный шаблон обложки

Цель: отделить оформление обложки от месячных страниц.

Работы:

1. Создать `CoverPage`.
2. Добавить фотографию, название, год, логотип и SVG-декор.
3. Создать отдельный набор редактируемых параметров обложки.
4. Учитывать bleed, safe area и зону пружины.

Критерий готовности:

- обложка редактируется независимо от шаблона месяца;
- проект содержит 13 подготовленных страниц.

## Этап 9. Инструменты layout-редактора

Цель: позволить пользователю править макет без изменения кода.

Работы:

1. Выделение, перемещение и изменение размеров элементов.
2. Привязка к направляющим и другим объектам.
3. Выравнивание и распределение.
4. Слои и `zIndex`.
5. Lock, hide, duplicate и delete.
6. Панель точных координат в миллиметрах.
7. Undo/Redo на основе команд или транзакций модели.
8. Визуальное отображение overflow и других диагностик.

Критерий готовности:

- пользователь может изменить шаблон, сохранив точную печатную геометрию;
- Undo/Redo восстанавливает модель без накопления ошибок.

## Этап 10. Сохранение проекта и шаблонов

Цель: сделать проекты переносимыми и долговечными.

Работы:

1. Зафиксировать версионированный `project.json`.
2. Создать контейнер проекта с изображениями, SVG и шрифтами.
3. Добавить миграции формата проекта.
4. Реализовать сохранение дизайна как шаблона.
5. Реализовать `Duplicate project for another year`.
6. Разделить `Сохранить` и `Сохранить как…`: после первого выбора файла хранить

7. Перенести восстановление в меню `Файл`, а шаблоны отделить от списка страниц.

Критерий готовности:

- проект открывается на другом компьютере без потерянных assets;
- новый год пересчитывает календарь, сохраняя дизайн.
- повторное сохранение не открывает выбор нового имени и каталога.

## Этап 11. PDF-экспорт

Цель: получить многостраничный PDF без скриншотов браузера.

Работы:

1. Ввести независимый интерфейс `PdfExportEngine`.
2. Передавать в экспорт `DocumentModel`, а не DOM.
3. Сохранять векторный текст и SVG.
4. Встраивать разрешённые шрифты.
5. Помещать изображения с достаточным эффективным DPI.
6. Записывать физические размеры, MediaBox, TrimBox и BleedBox.
7. Поддержать включаемые crop marks.
8. Создать 13-страничный PDF.
9. Встроить XMP-метаданные PDF/X-4 и выбранный ICC OutputIntent типографии.

Критерий готовности:

- PDF имеет правильное число страниц и физические размеры;
- текст остаётся векторным;
- шрифты встроены;
- страницы визуально совпадают с независимым preview.

## Этап 12. Предпечатная проверка

Цель: не допустить отправку технически неисправного макета.

Проверки:

- overflow текста;
- отсутствующие изображения, SVG и шрифты;
- слишком низкий эффективный DPI после кадрирования;
- элементы за пределами допустимой области;
- важный текст в зоне пружины;
- корректность bleed, trim и safe area;
- число и порядок страниц;
- наличие и встраивание необходимых глифов;
- итоговая визуальная проверка всех страниц после рендеринга PDF.

Критерий готовности:

- экспорт сообщает об ошибках до создания финального файла;
- PDF повторно открывается, анализируется и рендерится без дефектов.

## Этап 13. Производительность и эксплуатационная готовность

Цель: редактор остаётся отзывчивым на полном проекте из 13 страниц и не делает
повторную тяжёлую работу без необходимости.

Работы:

1. Измерять холодное открытие, повторное открытие, смену года, создание полного
   календаря, Undo/Redo, сохранение и PDF-экспорт.
2. Разбирать `MemoryDays.xml` только один раз за сеанс и переиспользовать
   неизменяемый набор записей.
3. Держать рассчитанные календарные годы в ограниченном кэше.
4. Не помещать исходный XML и вычисленный календарь в реактивную модель проекта,
   историю действий и файлы сохранения.
5. Загружать тяжёлый PDF-движок только при экспорте.
6. Добавить визуальную регрессионную проверку всех 12 месяцев для трёх шаблонов,
   форматов A3/A4 и страниц на 4, 5 и 6 недель.
7. Профилировать SVG-preview с реальным количеством надписей и устранять лишние
   повторные вычисления layout.

Критерий готовности:

- повторная смена уже рассчитанного года не запускает XML-парсер;
- редактирование и автосохранение не обходят 3811 исходных XML-записей;
- тяжёлый код PDF не входит в начальный исполняемый модуль;
- контрольная матрица месяцев не имеет наложений, обрезанных знаков и
  незамеченного переполнения.

## Текущий статус: восемь завершающих блоков выполнены

1. **Данные и посты.** Есть два версионированных профиля: строгий монастырский
   `typikon-strict` и отдельная приходская таблица `parish`. Переходящие периоды
   считаются от Пасхи, фиксированные — через юлианскую дату; XML сообщает события
   и ранги, но не подменяет алгоритм трапезы. Ответ содержит причину, профиль,
   версию правил и источники.
2. **Отбор текста.** Пасха, двунадесятые, великие и средние записи обязательны и
   не исчезают из-за числового лимита. Малые берутся только при отсутствии
   значимых и только пока помещаются. Полное/короткое/очень короткое название и
   пользовательский минимум кегля применяются общим алгоритмом preview/PDF.
3. **Месячная страница.** Календарь растянут до нижней легенды, отдельной полосы
   цитаты нет. Заголовки единообразны, числа и картинки увеличены. Легенда одна
   строка, включает только применённые режимы и не содержит «поста нет» или
   объяснения воскресенья. Проверяются 12 месяцев, 4–6 строк недель, A3–A6 и три
   шаблона.
4. **Предпечатная проверка.** Контролируются overflow, DPI, trim/bleed/safe,
   защитная зона переплёта, отсутствующие глифы, состав и порядок страниц,
   метки реза, PDF/X-4 и ICC OutputIntent. PDF строится непосредственно из модели.
5. **Мастер и повторное использование.** Выбранный месяц применяется как
   мастер-страница после предварительного описания; назначения фотографий
   сохраняются, действие отменяется. Есть пользовательские шаблоны проекта,
   отдельная библиотека шаблонов календарной сетки с применением к одному или
   всем 12 месяцам и создание независимой копии на другой год.
6. **Проекты и шрифты.** Контейнер `.kalendar` включает assets и пользовательские
   шрифты, старые JSON открываются через миграцию. Есть `Сохранить как…`, недавние
   имена, автосохранение, именованные резервные точки и восстановление перед
   опасными заменами.
7. **Календарный API.** Контракт `1.0.0` экспортируется из
   `src/calendar/index.ts` и вызывается в браузере без сетевого сервиса: день,
   год, Пасха, профиль и версия правил. События монастыря подключаются отдельным
   массивом.
8. **Автоматическая проверка и скорость.** Модульные тесты, Playwright E2E,
   растровая регрессия PDF, структурная матрица из 144 комбинаций и benchmark
   включены в стандартный выпускной прогон.

## Дополнение: свободная геометрия объектов дня

У календарной ячейки независимо задаются размер и координаты X/Y от её левого
верхнего угла для числа, даты по старому стилю, текста, знака поста и знака
типикона. В интерфейсе нет искусственных верхних пределов: допустимы, например,
6 и 100 pt. Изменение кегля или общего padding не двигает и не масштабирует уже
заданный знак. Межстрочное расстояние и отступ между разными событиями
настраиваются отдельно. Эти свойства входят в мастер-страницу, шаблоны сетки,
контейнер и миграцию.

## Оставшиеся выпускные задачи

Функциональная сквозная версия работает, но перед публичным выпуском ещё нужны:

1. Ручная церковно-календарная приёмка контрольных лет ответственным лицом
   монастыря; автоматические тесты доказывают работу заложенных правил, но не
   заменяют содержательную проверку устава и локальных исключений.
2. Контрольный типографский тираж с выбранным ICC-профилем, реальной бумагой,
   обрезкой и пружиной; экран и программный анализ PDF не проверяют физический
   результат печати.
3. Производственная упаковка приложения: адрес развёртывания либо настольная
   сборка, автоматическое обновление, политика резервного копирования и инструкция
   переноса проекта на другой компьютер.
4. Матрица поддерживаемых браузеров. Полноценная повторная запись в выбранный файл
   доступна в браузерах с File System Access API; для остальных остаётся безопасное
   скачивание новой копии, что должно быть явно указано в выпускной инструкции.
5. Финальная проверка доступности интерфейса: порядок Tab, фокус диалогов,
   контраст, работа без мыши и экранный диктор.

## Выпускная проверка

```text
npm run typecheck
npm test
npm run test:e2e
npm run test:visual
npm run benchmark
npm run build
```

Эталонные изображения обновляются только осознанно командой
`npm run test:visual:update` после визуального просмотра результата.
